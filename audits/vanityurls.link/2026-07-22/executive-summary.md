# Executive Summary

## Mandate, Boundary, And Bottom Line

This audit assessed whether vanityURLs can survive the sudden departure or changed interests of its creators and current maintainers. It covered the product source, Terraform source of truth, reference-instance source, website/documentation source, local `docs/`, public Git history, and public GitHub pull requests, issues, projects, releases, and Actions through **July 22, 2026**. It used public, read-only evidence only. No authenticated repository settings, cloud accounts, registrar records, secrets, Terraform state, billing records, live deployment records, or private operating procedures were available. No local dependency restore, test, build, Terraform operation, deployment, or recovery exercise was performed.

The answers depend on which continuity outcome is intended:

| Audit question | Answer | Evidence-bounded reason |
|---|---|---|
| Can a new maintainer take over the canonical project with minimal creator involvement? | **Not established from public evidence.** | The code and public decision history are strong. The public corpus does not show whether normally private appointment, authority, recovery, and successor-access arrangements exist, so it cannot support either a yes or no answer. |
| Can a third party establish and operate a new, independently controlled vanityURLs instance? | **Plausible, but not yet proven easy.** | The stateless, Git-backed design, MIT license, setup/detach/upgrade tooling, tests, and operator documentation support this outcome. A non-creator has not been observed completing setup, release, deployment, rollback, and recovery with measured assistance. |
| Can a third party take over and operate the existing project, `v8s.link` domain, and demo service? | **Unresolved; current-owner cooperation and private authority evidence are required.** | GitHub, Cloudflare, registrar/domain, Terraform state, secrets, deployment, alert, renewal, and recovery custody are normally private. Their absence from this corpus does not show poor operations, but actual takeover cannot be accepted until transferability is verified. |
| If the creators abandon the project, can someone else pick it up and evolve it? | **Yes for a fork, probably with moderate effort; no assurance for canonical continuity.** | Public source, tests, documentation, ADRs, release history, and a low-state runtime provide a credible technical foundation. Preserving the existing identity, trusted releases, domain, and service requires controls not demonstrated here. |

The most important conclusion is that vanityURLs does **not** need a wholesale rewrite to become successor-ready. The public evidence supports its technical portability and directly identifies upgrade-authentication, demo/source-alignment, and governance work. Canonical continuity remains an unresolved transfer question rather than a negative judgment about unseen private operations.

## Current Product And Control Position

| Area | Largest strengths | Direct concerns and decision dependencies |
|---|---|---|
| **Architecture** | Stateless Cloudflare Worker; no application database or queue; no runtime npm dependency surface; human-authored Git configuration compiled into a read-only registry; clear default/custom/generated boundaries; public architecture decisions; optional analytics can remain disabled. | Product, instance, infrastructure, and documentation authority is split across four repositories and external GitHub, Cloudflare, registrar, DNS, Terraform-state, secret, and release-signing surfaces. Those private controls must be verified for an actual takeover; the public corpus does not establish that they are absent. |
| **Code** | Broad source-level tests cover Worker, registry, build, setup, detach, upgrade, validation, policy, and security behavior. One integrated product check combines formatting, build, lint/hygiene/complexity checks, and 14 test scripts; cutoff-eligible hosted checks succeeded. | No clean local audit run was performed and no coverage percentage is available. Critical orchestration remains concentrated in large Worker/build/setup/upgrade modules, with complexity limits warning-only. `v8s-config` and `v8s-link` lack public CI/review history; website package quality is not hosted-gated. The upgrade path does not authenticate a selected release tag before refreshed code can execute. |
| **Operationalization** | Setup, detachment, upgrade, release, rollback, security, Terraform intent, and link-operation guidance are unusually extensive for a small OSS redirector. Git-backed configuration and a managed edge runtime reduce the number of components a successor must operate. | Public evidence does not establish succession, authority/custody, Terraform-state recovery, alert ownership, renewal, capacity, or handover records; these are verification items for canonical takeover, not inferred operational defects. The official instance is source-pinned to 3.6.3 while the cutoff product release is 3.7.0, with no proof of the deployed version. |
| **Documentation** | Approximately 97 catalogued documentation records, bilingual public material, 19 existing ADRs, extensive configuration/operation guidance, and meaningful rationale for important design choices. | Governance contradicts itself on maintainer concentration; auxiliary repositories lack a common contribution/ownership model; one contribution issue URL is obsolete; the website has no lockfile or hosted package-quality gate; security upgrade guidance conflicts with implementation; demo inventory differs from its stated source; no succession, account-transfer, recovery-exercise, or third-party acceptance record exists. |

The project and website show sustained public activity: the product repository had 75 pull requests and 38 releases by the cutoff; the website had 42 pull requests and 38 releases. Feature-level attribution identifies two public contributors responsible for 41 of 43 supported units (95.3%), and one responsible for 86.4% of the last cutoff-anchored year. This identifies handover learning paths, not authority, employment performance, or transfer readiness. Conversely, `v8s-config` and `v8s-link` had no public pull requests, issues, releases, or Actions and only three and one commits respectively. The repositories closest to live operation therefore carry the least public change-control evidence. See the [contributor value assessment](controls/contributors/contribution-value.md), [GitHub history and hosted CI packet](evidence/packets/github-history-and-hosted-ci.md), [delivery and quality packet](evidence/packets/delivery-and-quality.md), and [release/change-control view](controls/project-health/release-change-control.md).

## Material Risks, Unknowns, And Decisions

### Decision-Useful Conclusions

1. **Define continuity as two separate outcomes.** An independently owned fork is technically plausible; takeover of the canonical repositories, release trust, domain, and demo is not established. The current maintainers and project creators must decide which assets the community promises to preserve before “third-party operable” can be used consistently. Smallest next move: approve [OI-001](controls/open-items.md).
2. **Verify authority and custody if canonical takeover is selected.** GitHub administration, signers, Cloudflare ownership, registrar control, Terraform state, secrets, deploy paths, and recovery recipients are normally private and therefore neutral in this public assessment. They become acceptance evidence for the specific takeover decision. Smallest next proof: [OI-002](controls/open-items.md) and [OI-006](controls/open-items.md), followed by the independent exercise in [OI-004](controls/open-items.md).
3. **Correct two immediate public trust gaps.** Upgrade source is selected by stable tag but not signature-verified before refreshed code can execute, and the official demo’s “current” inventory does not match its stated source repository. These are implementation/documentation mismatches, not merely unavailable private evidence. Smallest actions: [OI-010](controls/open-items.md) and [OI-014](controls/open-items.md).
4. **Extend the product repository’s quality discipline to the operating system around it.** The strongest tests and hosted checks are in `code`; the Terraform, instance, and website repositories are the weak links for a successor. Smallest actions: [OI-007](controls/open-items.md) and [OI-008](controls/open-items.md).
5. **Preserve the stateless, analytics-disabled baseline.** It minimizes vendor, privacy, recovery, and cost scope. Add stateful infrastructure or analytics only after measured capacity or product evidence justifies the new handover burden. Smallest proof before architectural expansion: [OI-011](controls/open-items.md).
6. **Use the attributed contribution history to stage the handover.** It identifies the primary technical and documentation learning paths, but cannot appoint a maintainer or prove control. Smallest next proof: execute [OI-004](controls/open-items.md) against the [feature/change units](controls/contributors/contribution-value.md).

### Decisions Now

- **[OI-001 — continuity scope](controls/open-items.md):** Current maintainers and project creators, with community-visible approval, must decide whether succession preserves the canonical repositories, trusted release lineage, domain, demo service, and community identity or only guarantees that an independent fork can be created. Publish assets in/out, decision authority, and acceptance criteria.

### Evidence Needed

- **[OI-002 — authority and custody redundancy](controls/open-items.md):** Current asset/account owners should prove two recoverable successor paths for GitHub administration, protected branches/tags, release signing, Cloudflare, domain registration, deployment, and public contacts.
- **[OI-006 — existing demo control plane](controls/open-items.md):** Current infrastructure/domain operators should reconcile Terraform backend/state/import coverage, drift, DNS/domain/Cloudflare ownership, quotas, alerts, deployment connection, last-known-good artifact, and recovery evidence.
- **[OI-013 — renewal, plan, quota, and billing register](controls/open-items.md):** Current asset/account owners should produce a redacted register with accountable and backup owners, renewals, relevant quotas, notifications, and transfer routes. No numeric cost conclusion is currently supported.
- **[OI-004 — non-creator acceptance exercise](controls/open-items.md):** A prospective successor or independent operator should complete clean setup, representative build/check, release, deploy, smoke, rollback, and recovery tasks in an isolated environment, recording time, assistance, failures, and results.
- **[OI-011 — capacity and degradation envelope](controls/open-items.md):** An independent operator with maintainers should measure registry growth, build/check/deploy time, request bursts, rate limits, provider quotas, alert behavior, degradation, rollback, and stop thresholds in an isolated environment.

### Implementation Corrections

- **[OI-010 — authenticated upgrade source](controls/open-items.md):** Product maintainers and release signers should make upgrade stop unless the selected tag is verified against an approved trust policy, test the failure path, and align public security guidance.
- **[OI-014 — demo and claim reconciliation](controls/open-items.md):** Website and demo maintainers should publish the deployed commit/inventory source, automate drift checks, correct stale inventory, and qualify or substantiate “free, fast, and always under your control.”
- **[OI-012 — redundant monitoring and incident ownership](controls/open-items.md):** Current operators and at least one successor should own and test alerts for domain renewal, DNS/TLS, Worker errors, Access, security events, deploy failures, public contacts, and recovery actions.
- **[OI-007 — operational repository change control](controls/open-items.md):** Current maintainers/infrastructure operators should add reviewable, least-privilege validation and deploy/rollback records for `v8s-config` and `v8s-link`.
- **[OI-008 — reproducible, quality-gated website](controls/open-items.md):** The website maintainer should commit a dependency lock, align version manifests, and run build/test/lint/internal-link checks on pull requests and `main`.
- **[OI-005 — cross-repository governance](controls/open-items.md):** Current maintainers should publish one maintainer/contribution/security map, resolve contradictory governance language, and correct obsolete links.
- **[OI-003 — succession and third-party operations packet](controls/open-items.md):** After continuity scope and authority inventories are approved, current maintainers should create one maintained handover packet and validate it through the non-creator exercise.
- **[OI-009 — incremental complexity ratchet](controls/open-items.md):** Product maintainers should decompose critical orchestration only when touched, preserve focused tests, and convert selected stable warning budgets to errors without a broad rewrite.
