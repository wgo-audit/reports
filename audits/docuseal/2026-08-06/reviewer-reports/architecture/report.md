# Architecture

## Audit Question, Depth, And Evidence Boundary

Does pinned DocuSeal Community `3.1.7` expose components, dependencies, data, runtime boundaries and material technical decisions clearly enough to support safe further evaluation for regulated web/mobile onboarding? This detailed review is cutoff at 2026-08-06 and uses direct source at `a2d8b855491793870b7b4acf176d2d95ae95ff83`, the approved `docuseal.com` pages, and cutoff-bounded GitHub history/Actions evidence. The [component packet](../../evidence/packets/architecture-component-api-ui-contracts.md), [data/jobs packet](../../evidence/packets/architecture-data-jobs-migrations-provenance.md), [runtime packet](../../evidence/packets/architecture-runtime-deployment-delivery-identity-secrets.md), [public deployment packet](../../evidence/packets/architecture-approved-public-deployment-docs.md), and [shared GitHub packet](../../evidence/packets/github-history-and-hosted-ci.md) preserve exact locators and limitations.

Excluded: Pro implementation, hosted Cloud assessment, penetration/load testing, remediation, target/live-environment proof, legal/regulatory conclusions and production approval. Source topology does not prove operation, ownership, approval, cost or control effectiveness.

Coverage includes component/UI/API boundaries; implicit and public contracts; SQL/blob authority and lifecycle; synchronous/asynchronous completion; signing/audit/verification pipeline; container/runtime/dependencies; delivery/migrations; human/API identity and secret roots; release provenance; operations and capacity signals. Material unresolved routes are proposed as OI-001 through OI-006: edition/integration authority, signing trust authority, target runtime/capacity proof, controlled release/migration action, integration-contract verification, and evidence lifecycle verification.

No approved live environment, workload, datastore/object store, IdP, secret manager, key/TSA, deployment digest, telemetry, backup/restore, retention, support or cost evidence exists. Deployment-template repositories, external embed packages and Docker registry artifacts are **Documented outside audited scope; not independently verified.** The smallest useful expansion is release-specific vendor/package evidence and immutable registry metadata after the edition path is chosen.

## Mandate-Relevant Strengths

- The source boundary is reproducible, and its main modules, routes, stores, jobs and generated-artifact path are traceable with exact locators.
- The completion pipeline captures signer/event metadata, result hashes and webhook attempt records; generated PDFs can use PKCS/TSA signing. These mechanisms provide inspectable starting points, while their live configuration and sufficiency remain unproved.
- PostgreSQL and private object-store choices are supported in source; the container separates `/app` from the default writable `/data/docuseal` path and includes a health endpoint.
- CI for the pinned commit ran lint, static analysis and RSpec successfully, and the version-tag image build completed for AMD64/ARM64. These reduce uncertainty about the assessed snapshot but do not establish production readiness.

### Decision Insights

- **Decide edition/integration architecture before client implementation.** The causal conflict is implemented Community API/webhooks versus hosted/Pro-oriented contracts and external embedding. A wrong choice can strand web/mobile work. Smallest next proof: vendor-supplied release-specific entitlement/component/contract matrix, then OI-001 authority decision.
- **Decide the signing/evidence trust model before specialist acceptance testing.** Conditional signing, application-held PKCS material and snapshot-based audit records determine what specialists can evaluate. A wrong default can make later evidence unusable. Smallest next action: OI-002 key/certificate/TSA/verification decision, then OI-006 artifact tests.
- **Separate production topology from convenience defaults before load/recovery conclusions.** Embedded worker/Redis, boot migrations and split SQL/blob state couple failures. Assuming retry code equals resilience can lose onboarding state. Smallest next proof: OI-003 target topology plus failure/capacity tests and OI-004 controlled release runbook.
- **Promote immutable artifacts, not tags.** Green upstream jobs do not bind a deployed digest to reviewed source. A wrong artifact invalidates every downstream result. Smallest next action: OI-004 digest/SBOM/provenance intake and promotion evidence.

## Reconciliation

The material evidence conflict is edition applicability: the mandate/public packaging treats required integration capabilities as Pro dependencies, while pinned Community source exposes some API/webhook implementation and a hosted/OpenAPI document includes additional Pro paths. Each source establishes a different boundary; the report leaves entitlement/compatibility unresolved and routes it to vendor proof rather than treating Pro absence as a defect. GitHub PR #691/issue #469 and release `3.1.3` are used only as migration leads; pinned source establishes current boot behavior. No baseline or prior architecture items exist, and no other material source conflict was found.

## Bounded Conclusion And Downstream Guidance

The Community source is architecturally intelligible enough to **continue conditionally** into target-architecture definition, vendor evidence requests and specialist discussions. It is not evidence of production readiness. The conditions are edition/integration proof, signing/evidence trust authority, explicit externalized runtime/data topology, controlled migration and immutable release promotion, lifecycle/recovery proof, and load/operations validation.

Code Quality may rely on the located component/contract boundaries but must not infer correctness. Product Value may use edition/workflow dependencies but must not infer entitlement or acceptance. Security/Privacy must inspect identity, key and data boundaries without assuming control effectiveness. Continuity, Scalability, Maintenance and Expense reviewers must treat source defaults and public sizing as inputs, not live reliability, capacity or cost.
