# Security And Privacy

## Audit Question, Depth, And Evidence Boundary

At detailed depth, this review asks what material identity, credential, route, exposure, personal-data, key-management, vulnerability, and supply-chain risks are evidenced in DocuSeal Community `3.1.7`, and what must be decided or proved before production approval for regulated web/mobile onboarding. Evidence is pinned Community source at `a2d8b855491793870b7b4acf176d2d95ae95ff83`, the [identity/secrets/data packet](../../evidence/packets/security-identity-secrets-data-boundaries.md), [edge/runtime packet](../../evidence/packets/security-edge-runtime-exposure.md), [vulnerability/supply-chain packet](../../evidence/packets/security-vulnerability-supply-chain.md), cutoff-bounded GitHub/CI evidence, and approved `docuseal.com` pages used only as post-cutoff validation.

Excluded: live or hosted DocuSeal Cloud assessment, penetration testing, unapproved network probing, secret or customer-record inspection, Pro implementation, code remediation, target control-effectiveness testing, legal/regulatory/privacy conclusions, and production approval. Source/configuration establishes mechanisms and attack surfaces, not exploitability, live exposure, control effectiveness, or specialist acceptance.

Effort uses the audit-wide correction boundary: `S` is one bounded component/test area, `M` crosses components or requires coordinated validation, and `L` spans major surfaces, platforms, or owners.

## Coverage And Material Gaps

The review covered human and machine identity, Community authorization, MFA/session settings, signer capability access, first-user bootstrap, API tokens, secret roots and consumers, signing-key storage, PII/files/derivatives, archive/deletion paths, webhook data egress, public and privileged routes, Compose ingress, TLS/header/CORS configuration, abuse controls, remote imports, webhook/TSA/SMTP/storage egress, dependency/build provenance, security-tool gates, and vulnerability-response documentation.

No live IAM, network, TLS, WAF, secret manager, key, storage, database, backup, log, egress, image, vulnerability, deletion, or incident evidence was approved. Release-specific Pro security evidence and organization security/privacy standards were not supplied. These gaps route through existing OI-001–OI-006 and proposed Security items below.

## Mandate-Relevant Strengths

- Central authentication/authorization gates, account predicates, active-user lookup, optional TOTP/email verification, signed-purpose tokens, reveal throttling, request parameter filtering, and encrypted credential/configuration fields provide inspectable control mechanisms.
- Signer and file routes apply workflow-state, capability, signed-token, and selected access checks; source makes the trust boundaries testable even though target adequacy is unproved.
- Webhooks use finite timeouts, persisted attempts, and HMAC signatures; remote imports revalidate HTTPS redirects. These reduce specific risks while leaving destination/network policy unresolved.
- The pinned commit's RuboCop, ERB lint, ESLint, Brakeman, RSpec, and Docker jobs passed, and the repository provides a private vulnerability-reporting address and bug-bounty statement. These are useful maintenance signals, not a vulnerability or response guarantee.

### Decision Insights

1. **Choose identity and edition controls before integration design.** Community's one-role model and link/email signer assurance do not satisfy an unstated organizational standard by themselves. The smallest next action is an authority-approved operator/signer assurance matrix under OI-011, then release-specific Pro evidence under OI-001.
2. **Treat first boot, ingress and egress as security design work, not container defaults.** Direct port publication, shared route exposure, conditional SSL, process-local throttling, and operator-selected destinations are source facts whose consequences depend on the target. The smallest proof is an approved route/listener/egress matrix with negative reachability, header, abuse, SSRF and bootstrap tests.
3. **Separate signing trust from application secret encryption.** Co-resident exportable key material and shared root derivation cannot establish independent custody or recoverable rotation. OI-002 must precede specialist artifact acceptance under OI-006.
4. **Require an organization-owned artifact and vulnerability gate.** Green upstream CI does not bind deployed digest, dependency state or patch response. Extend OI-004 with SBOM, provenance, vulnerability and promotion evidence plus a defined vendor/advisory intake process.

## Bounded Conclusion And Downstream Guidance

Security/Privacy supports **continue evaluation conditionally**, not production approval. Community `3.1.7` exposes useful, inspectable controls, but the current evidence does not establish least privilege, target identity/KYC assurance, comprehensive route authorization, independent key custody, private-data lifecycle, effective ingress/egress/abuse protection, current vulnerability state, immutable artifact provenance, or production control effectiveness.

Business Continuity should use the identity, secret, store, route and egress dependencies without inferring effective recovery or ownership. Expense and Scalability may use the control/topology gaps as work drivers, not live cost/capacity evidence. Revenue Risk and Project Health may use the bounded posture after their dependencies complete but must not claim compromise, compliance, defect prevalence, Pro weakness, or production unsuitability beyond the cited evidence.
