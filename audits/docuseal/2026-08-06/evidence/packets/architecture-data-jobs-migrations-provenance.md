# Architecture Evidence Packet — Data, Jobs, Migrations, Artifacts, and Provenance

## Scope And Evidence Boundary

- Pinned source: `docusealco/docuseal` tag `3.1.7`, commit `a2d8b855491793870b7b4acf176d2d95ae95ff83` (verified locally with `git rev-parse HEAD` and `git describe --tags --exact-match HEAD`).
- Scope: implemented data stores/flows, asynchronous work, migrations, generated artifacts, and provenance. Runtime deployment, API/UI topology, and identity/secrets conclusions are excluded except where needed to locate these boundaries.
- Status terms: **Observed** means directly implemented in pinned source; **Inferred** means an architectural consequence that requires runtime validation; **Unknown** means the approved evidence does not establish it.

## Observations

### 1. Relational system of record and file-object split

- **Statement / locator — Observed:** Production supports PostgreSQL through discrete connection variables, SQLite when no database URL is set, PostgreSQL through `DATABASE_URL`, or MySQL through Trilogy; the configured pool is the sum of Puma and Sidekiq thread counts (`docuseal/config/database.yml:1-37`). Submissions store lifecycle timestamps plus serialized template/field/submitter/variable state and own submitters and submission events (`docuseal/app/models/submission.rb:44-74`). Submitters store signer coordinates, IP/user agent/timezone, serialized values/preferences/metadata, and own generated documents, uploaded attachments, preview documents, and events (`docuseal/app/models/submitter.rb:42-65`). Binary objects are Active Storage blobs, while polymorphic attachments carry the owning record, logical name, and UUID (`docuseal/db/schema.rb:68-93`).
- **Affected boundary:** application writes relational workflow/evidence records to the selected SQL database and file bytes to disk or object storage through Active Storage.
- **Limitation / gap:** Schema compatibility is not uniform: partial indexes are present in the pinned PostgreSQL schema (`docuseal/db/schema.rb:377-381`) but are conditionalized or omitted by some migrations for other adapters (`docuseal/db/migrate/20260701165617_add_index_on_submissions_completed_at.rb:3-16`). No approved evidence establishes equivalence, production sizing, or behavior under the auditor's workload.
- **History target / ADR candidate:** `config/database.yml`, `app/models/submission.rb`, `app/models/submitter.rb`, `db/schema.rb`. ADR candidate: select one production database and define transactional/adapter compatibility requirements.

### 2. Attachment service is selected at boot or reloaded from encrypted database configuration

- **Statement / locator — Observed:** Production chooses S3, GCS, Azure, or disk from environment variables and otherwise uses disk; proxy routing and URL expiry are configured separately (`docuseal/config/environments/production.rb:39-52`). Disk stores under `$WORKDIR/attachments`; S3/GCS/Azure definitions retain credentials and public/private selection in `storage.yml` (`docuseal/config/storage.yml:1-33`). In single-tenant production with no storage environment configured, an encrypted SQL record can replace the active service registry at runtime (`docuseal/lib/load_active_storage_configs.rb:18-46`; `docuseal/app/models/encrypted_config.rb:23-36`; `docuseal/app/controllers/storage_settings_controller.rb:10-32`). Each blob records its service name (`docuseal/db/schema.rb:80-93`).
- **Affected boundary:** SQL metadata/configuration -> Active Storage service registry -> disk/object-store bytes -> proxied or presigned consumer URLs.
- **Limitation / gap:** **Unknown:** the repository does not establish the organization's chosen store, replication, backup, object-lock/versioning, encryption-key ownership, cross-service migration procedure, or deletion verification. Catalog row `Data stores, migrations, retention, deletion, and residency` is `partial` and states these operational materials are absent (`_whats-going-on-20260806/documentation/catalog.md:78`).
- **History target / ADR candidate:** `config/storage.yml`, `config/environments/production.rb`, `lib/load_active_storage_configs.rb`. ADR candidate: storage system of record, migration strategy, retention/deletion, and evidence-preservation controls.

### 3. Signing completion crosses a database transaction into an asynchronous finalization pipeline

- **Statement / locator — Observed:** Form values and completion evidence are written in a database transaction; on completion the submitter gets `completed_at`, IP, user agent, timezone, and a `complete_form` event with IP, UA, session ID, and authenticated user ID when present (`docuseal/lib/submitters/submit_values.rb:44-78`; `docuseal/lib/submission_events.rb:14-21`). After commit, completion updates the parent submission and enqueues `ProcessSubmitterCompletionJob` (`docuseal/lib/submitters/submit_values.rb:22-41`). The worker creates completion summary rows, generates result PDFs, optionally generates a combined PDF, generates the audit PDF for the last signer, records completed-document hashes, then enqueues email and webhook handoffs (`docuseal/app/jobs/process_submitter_completion_job.rb:9-50`, `:52-95`, `:98-174`).
- **Affected boundary:** synchronous signer request -> SQL workflow/evidence records -> Redis/Sidekiq job -> generated Active Storage artifacts -> email/webhook consumers.
- **Limitation / gap:** **Inferred:** transaction commit and job enqueue are separate operations; no transactional outbox is present at these locators, so atomic persistence of both is not established. The worker is retry-driven and its steps span multiple SQL/object-store/external side effects; end-to-end exactly-once completion is not established by source.
- **History target / ADR candidate:** `lib/submitters/submit_values.rb`, `app/jobs/process_submitter_completion_job.rb`. ADR candidate: completion workflow consistency, recovery, replay, and reconciliation contract.

### 4. Background work uses Sidekiq and Redis embedded in the web-server lifecycle by default

- **Statement / locator — Observed:** Production Active Job uses Sidekiq (`docuseal/config/environments/production.rb:29`). Queues include default, webhooks, SMS, images, mailers, recurrent, and Rollbar (`docuseal/config/sidekiq.yml:1-8`). For non-multitenant operation, Puma loads both embedded Sidekiq and Redis plugins (`docuseal/config/puma.rb:52-57`). Sidekiq starts inside Puma, waits for Redis, uses `SIDEKIQ_THREADS` (default 5), and sets maximum retries to 13 (`docuseal/lib/puma/plugin/sidekiq_embed.rb:36-73`). If no external `REDIS_URL` is supplied, boot synthesizes a local URL and marks it for an embedded Redis process (`docuseal/config/dotenv.rb:103-110`); that process runs from `$WORKDIR` and Puma stops or restarts when Redis exits (`docuseal/lib/puma/plugin/redis_server.rb:7-36`, `:50-68`).
- **Affected boundary:** web lifecycle -> embedded worker -> Redis queue/schedules -> database/object-store/external side effects.
- **Limitation / gap:** **Unknown:** queue durability, dead-set handling, backlog monitoring, worker isolation, shutdown drain, replay ownership, and multi-replica operating topology are not documented or runtime-tested. Catalog row `Background jobs, horizontal scaling, and capacity model` is `not-found-in-corpus` (`_whats-going-on-20260806/documentation/catalog.md:79`).
- **History target / ADR candidate:** `config/puma.rb`, `lib/puma/plugin/sidekiq_embed.rb`, `lib/puma/plugin/redis_server.rb`, `config/sidekiq.yml`. ADR candidate: external versus embedded Redis/worker topology and failure/recovery semantics.

### 5. Generated PDF artifacts carry hashes and conditional cryptographic signatures

- **Statement / locator — Observed:** Result PDFs are generated from submission/template inputs. When both a signing reason and account PKCS material exist, the PDF is signed using the certificate, private key, and certificate chain, optionally with a timestamp handler; otherwise it is written without a cryptographic signature (`docuseal/lib/submissions/generate_result_attachments.rb:755-804`, `:821-833`). Each generated result attachment stores its source document UUID and a URL-safe Base64 SHA-256 of the generated bytes in attachment metadata (`docuseal/lib/submissions/generate_result_attachments.rb:806-813`). The completion worker copies these hashes into `completed_documents` (`docuseal/app/jobs/process_submitter_completion_job.rb:90-95`).
- **Affected boundary:** template/source artifact + signer values -> rendered PDF bytes -> optional PKCS/TSA signing -> Active Storage result -> SQL hash registry.
- **Limitation / gap:** **Observed conditional behavior, unknown deployment state:** the source supports signed and unsigned output paths; it does not prove that PKCS material or a timestamp service is configured for a future deployment, nor that generated bytes are correct or independently preserved.
- **History target / ADR candidate:** `lib/submissions/generate_result_attachments.rb#build_pdf_attachment`, `app/jobs/process_submitter_completion_job.rb#create_completed_documents!`. ADR candidate: required signing mode, certificate/TSA ownership, timestamping, LTV expectations, and failure policy.

### 6. Audit and combined artifacts are derived snapshots, not an immutable event store

- **Statement / locator — Observed:** The audit generator builds a PDF from current submission/submitter state and `submission_events`, includes original and result hashes and generation time, signer coordinates/verification indicators, IP/session/user-agent/timezone, field values, and a chronological event log (`docuseal/lib/submissions/generate_audit_trail.rb:209-238`, `:246-305`, `:339-453`, `:458-526`). It signs the audit PDF only when PKCS material is available, then stores it as the submission's `audit_trail` Active Storage attachment (`docuseal/lib/submissions/generate_audit_trail.rb:33-69`). A combined artifact imports result pages and optionally newly built audit pages, then is optionally signed and stored as `combined_document` or `merged_document` (`docuseal/lib/submissions/generate_combined_attachment.rb:7-44`, `:61-86`).
- **Affected boundary:** mutable SQL workflow/event rows and file attachments -> rendered audit/combined PDF -> Active Storage -> download/email/API/webhook consumer.
- **Limitation / gap:** **Inferred:** provenance is snapshot-based. The event table is ordinary mutable relational storage (`docuseal/app/models/submission_event.rb:31-69`), and the audit attachment itself has no stored application-level SHA-256 at creation (`docuseal/lib/submissions/generate_audit_trail.rb:61-68`). Source does not establish append-only/immutable event retention, artifact notarization, independent preservation, or a chain binding the audit PDF to a later verifier.
- **History target / ADR candidate:** `lib/submissions/generate_audit_trail.rb`, `app/models/submission_event.rb`, `lib/submissions/generate_combined_attachment.rb`. ADR candidate: authoritative evidence record, immutability, regeneration policy, and independent verification model.

### 7. Database lock-event rows coordinate artifact generation, but the completion marker is separate from object creation

- **Statement / locator — Observed:** Result, audit, and combined generation use a SQL `lock_events` key and `start/retry/complete/fail` rows; duplicate workers poll for up to 90 seconds and a partial unique index permits one `start` and one `complete` per key (`docuseal/lib/submissions/ensure_result_generated.rb:14-50`, `:53-68`; `docuseal/lib/submissions/ensure_audit_generated.rb:15-52`, `:55-74`; `docuseal/lib/submissions/ensure_combined_generated.rb:15-52`, `:55-74`; `docuseal/db/schema.rb:260-267`). Artifact upload occurs before a separate `complete` insert.
- **Affected boundary:** competing workers -> SQL coordination records -> object-store write -> SQL completion marker.
- **Limitation / gap:** **Inferred:** this is duplicate-work suppression, not a transaction spanning SQL and object storage. A process failure after upload and before `complete`, or stale `start` state, relies on later retry/error behavior; no cleanup/reconciliation policy for orphaned blobs or stale locks is visible at these locators. Waiting workers return the attachment when the latest state is either `complete` or `fail`, so a failed peer may yield `nil` rather than itself regenerating (`ensure_audit_generated.rb:67-70`; `ensure_combined_generated.rb:67-70`).
- **History target / ADR candidate:** the three `ensure_*_generated.rb` modules and `db/migrate/20250915060548_create_lock_events.rb`. ADR candidate: durable generation state machine and orphan/stale-work reconciliation.

### 8. Repository verification combines a global generated-hash lookup with embedded PDF-signature verification

- **Statement / locator — Observed:** The verification action hashes uploaded bytes and tests `CompletedDocument.exists?` by SHA-256, then asks HexaPDF to verify every embedded signature against certificates loaded for the current account (`docuseal/app/controllers/api/tools_controller.rb:18-35`). `completed_documents.sha256` has a non-unique index and `submitter_id`, but no database foreign key (`docuseal/db/schema.rb:101-108`, `:583-625`); its model association is application-level (`docuseal/app/models/completed_document.rb:18-21`).
- **Affected boundary:** externally supplied PDF -> global hash registry and account trust store -> `verified/not_found` checksum status plus signature messages.
- **Limitation / gap:** **Observed:** the checksum query is not scoped to account, submission, or audit attachment and returns no provenance record. **Unknown:** whether this global membership result meets the organization's independent-verification or evidentiary requirements; legal/security specialist determination remains required.
- **History target / ADR candidate:** `app/controllers/api/tools_controller.rb#verify`, `app/models/completed_document.rb`, `db/schema.rb`. ADR candidate: verification identity/binding, tenant scope, retained provenance, and trust-anchor policy.

### 9. Webhook delivery has durable attempt records and application-level exponential retries

- **Statement / locator — Observed:** Event enqueue creates one UUID per source record and pushes jobs in bulk for each configured destination (`docuseal/lib/webhook_urls.rb:48-68`). Completed-form and completed-submission jobs serialize the current record/artifact URLs and retry after `2**attempt` minutes until their job-specific limits (`docuseal/app/jobs/send_form_completed_webhook_request_job.rb:19-39`; `docuseal/app/jobs/send_submission_completed_webhook_request_job.rb:19-35`). Sending creates or reuses a `(webhook_url, uuid)` event, signs the request body with HMAC when no explicit signature header exists, persists each response/error attempt, and marks event status (`docuseal/lib/send_webhook_request.rb:17-54`, `:64-113`). The database uniquely indexes event UUID per webhook URL, but webhook events/attempts have no database foreign keys in the pinned schema (`docuseal/db/schema.rb:545-568`, `:583-625`).
- **Affected boundary:** domain completion/archive/start event -> Redis job -> serialized current state and signed HTTP request -> remote consumer -> SQL delivery ledger.
- **Limitation / gap:** **Inferred:** event UUID deduplicates the local event record but does not make the remote side effect exactly once; consumers must deduplicate. Retention, reconciliation, manual replay governance, and handling after retry exhaustion are not established in approved documentation.
- **History target / ADR candidate:** `lib/webhook_urls.rb`, `lib/send_webhook_request.rb`, representative completion webhook jobs. ADR candidate: integration delivery contract, idempotency, retention, and operational replay.

### 10. Expiration is a scheduled queue event guarded against stale schedules

- **Statement / locator — Observed:** Creating or changing a submission expiration enqueues `ProcessSubmissionExpiredJob` at `expire_at` with both record ID and the scheduled epoch (`docuseal/app/controllers/api/submissions_controller.rb:107-118`; also `docuseal/lib/submissions/create_from_submitters.rb:181-182`). The job exits when the record is missing, archived, declined, completed, or its current expiration no longer matches the enqueued timestamp; otherwise it emits the expiration webhook (`docuseal/app/jobs/process_submission_expired_job.rb:6-18`).
- **Affected boundary:** SQL lifecycle timestamp -> Redis scheduled set -> guarded execution -> webhook queue.
- **Limitation / gap:** **Unknown:** delayed-job recovery after Redis loss, acceptable firing delay, schedule backlog monitoring, and reconciliation of missed expirations.
- **History target / ADR candidate:** `app/jobs/process_submission_expired_job.rb` and all `perform_at` callers. ADR candidate: scheduled lifecycle-event reliability and reconciliation.

### 11. Production boot automatically runs schema and data migrations through the application database connection

- **Statement / locator — Observed:** Every production application preparation runs `DatabaseTasks.migrate` unless `RUN_MIGRATIONS=false` (`docuseal/config/initializers/migrate.rb:3-4`). The pinned database configuration has only one production connection selection and no `MIGRATION_DATABASE_URL` (`docuseal/config/database.yml:14-37`). Release 3.1.3 warned that its automatic boot migration could take 1–2 minutes at one million submissions and seconds at 10–50k; this is maintainer-supplied, non-target benchmark evidence (`_whats-going-on-20260806/evidence/packets/github-history-and-hosted-ci.md:35`). The corresponding pinned backfill disables the DDL transaction, walks ID ranges of 10,000, updates completed submissions, and has a no-op `down` (`docuseal/db/migrate/20260701154120_populate_submission_completed_at.rb:3-38`). It references current `Submitter` and `Submission` application models inside the migration query (`:15-32`).
- **Affected boundary:** application boot -> selected production database connection -> ordered DDL/data migration -> web/worker availability.
- **Limitation / gap:** **Observed:** rollback cannot undo that backfill. **Unknown:** target-volume duration, pooled-connection compatibility, controlled rollout/rollback, and multi-replica startup procedure. Open issue #469 and draft PR #691 are only leads about pooled PostgreSQL migration failures/a separate migration URL; they are not pinned behavior or a confirmed defect (`_whats-going-on-20260806/evidence/packets/github-history-and-hosted-ci.md:38`, `:41`, `:58`).
- **History target / ADR candidate:** `config/initializers/migrate.rb`, `config/database.yml`, `db/migrate/20260701154120_populate_submission_completed_at.rb`. ADR candidate: explicit migration job/direct connection, backward-compatible rollout, rollback/restore gates, and maintenance-window policy.

### 12. Archive and permanent-delete paths have materially different provenance outcomes

- **Statement / locator — Observed:** Ordinary removal sets `archived_at` and emits a webhook; `permanently=true` destroys the submission (`docuseal/app/controllers/submissions_controller.rb:72-86`; API equivalent `docuseal/app/controllers/api/submissions_controller.rb:126-135`). Destroying a submission cascades in application code to submitters and submission events, and submitters cascade their event/version/generation rows (`docuseal/app/models/submission.rb:49-52`; `docuseal/app/models/submitter.rb:46-71`). However, `completed_submitters`, `completed_documents`, `webhook_events`, and `webhook_attempts` have no database foreign keys to their logical parents (`docuseal/db/schema.rb:101-126`, `:545-568`, `:583-625`), and there is no parent-side dependent association for completion-ledger rows at the submission/submitter models. Active Storage attachments are polymorphic and likewise lack a record foreign key (`docuseal/db/schema.rb:68-78`).
- **Affected boundary:** user/API archive or hard delete -> workflow/evidence rows -> artifact bytes -> completion and delivery ledgers.
- **Limitation / gap:** **Inferred:** hard deletion can leave completion/hash and webhook-attempt rows without their original application records unless another unobserved cleanup mechanism operates; archive intentionally retains them. The approved corpus does not define retention, legal hold, verified deletion, or which record is authoritative.
- **History target / ADR candidate:** submission destroy controllers, `app/models/submission.rb`, `app/models/submitter.rb`, completion/webhook migrations. ADR candidate: lifecycle matrix covering archive, purge, artifact deletion, audit preservation, legal hold, and ledger cleanup.

### 13. Release image provenance is tag-driven but not independently attested in the inspected workflow

- **Statement / locator — Observed:** A semantic-version tag triggers a multi-architecture Docker build; the workflow checks out source, writes the tag name into `.version`, logs into Docker Hub, and pushes `docuseal/docuseal` for AMD64 and ARM64 (`docuseal/.github/workflows/docker.yml:1-49`). The Dockerfile copies `.version` into the image and serves it from `public/version` (`docuseal/Dockerfile:76-85`). The shared collector observed a successful pinned-tag build/push run, but did not inspect the resulting digest (`_whats-going-on-20260806/evidence/packets/github-history-and-hosted-ci.md:37`, `:51`).
- **Affected boundary:** Git tag/source -> GitHub Actions -> Docker build -> Docker Hub image -> operator-selected deployment artifact.
- **Limitation / gap:** **Observed:** the workflow has no visible SBOM, image signing, attestation, vulnerability scan, or digest publication step; actions are referenced by mutable major tags (`docker.yml:14-49`). Some Dockerfile downloads are versioned and only PDFium is checksum-verified; fonts and the field-detection model are downloaded without checksums (`docuseal/Dockerfile:1-18`). **Unknown:** registry retention and the digest an operator would deploy.
- **History target / ADR candidate:** `.github/workflows/docker.yml`, `Dockerfile`. ADR candidate: release provenance/SBOM/signature, dependency pinning, digest promotion, and artifact retention.

## Material Unknowns And Access Limits

- No approved source supplies a complete Community data-flow/data-classification map, retention/deletion schedule, self-hosted backup/restore procedure, RPO/RTO, queue operating model, migration rollback runbook, or artifact-provenance procedure (`_whats-going-on-20260806/documentation/catalog.md:74-79`, `:87`).
- Source establishes possible mechanisms, not live configuration, completed job history, artifact correctness, immutability, deployed image identity, workload fitness, regulatory sufficiency, ownership, or production approval.
- The target architecture must explicitly resolve SQL adapter/version, external versus embedded Redis/workers, blob store and keys, completion/outbox reconciliation, migration execution, evidence retention, verifier binding, and signed-image promotion before production approval can be considered.

## Reuse Guidance

Reviewers may reuse the observed data, job, migration, artifact, and provenance boundaries with their stated status and limitations. They must not infer live configuration, completed processing, artifact correctness, or production approval.
