# Architecture Evidence Packet — Components, APIs, UI, and Shared Contracts

Pinned source: `docuseal/` tag `3.1.7`, commit `a2d8b855491793870b7b4acf176d2d95ae95ff83`. Evidence below was verified directly in the pinned source; CodeGraph was not invoked. Runtime/deployment, persistence internals, jobs, migrations, artifacts/provenance, and identity/secrets integration are excluded.

## 1. Application and component shape

- **Statement / locator:** The inspected Community application is a Rails application that loads Active Record, Active Storage, Action Controller/View/Mailer, Active Job, and bundled gems (`docuseal/config/application.rb:5-22`, `Docuseal::Application`). Its HTTP surface is one route set spanning authenticated dashboard/settings/template UI, JSON API, public signing links, MCP, and embed-script endpoints (`docuseal/config/routes.rb:12-226`, `Rails.application.routes.draw`). Domain behavior is grouped chiefly under `Templates`, `Submissions`, `Submitters`, and `WebhookUrls` Ruby modules (for example `docuseal/lib/templates.rb:3-8`, `docuseal/lib/submissions.rb:92-99`, `docuseal/lib/webhook_urls.rb:3-22`) around Rails models/controllers, not declared as separately versioned component packages.
- **Status / limitation:** **Observed.** This is source topology, not proof of a live deployment or operational ownership. The absence of separately packaged components does not prove they cannot be separated by unavailable code.
- **Boundary:** Rails web application ↔ domain modules/models; direct framework dependencies include Rails, Devise, CanCanCan, Active Storage, Turbo, Shakapacker, and Sidekiq (`docuseal/Gemfile:13-45`).
- **History target:** `config/application.rb` (`Docuseal::Application`), `config/routes.rb`, `lib/templates.rb`, `lib/submissions.rb`, `lib/submitters.rb`.
- **ADR / gap:** **ADR candidate:** record whether the organization accepts this modular-monolith boundary for the target integration and which modules it will own. No release-versioned component/ownership map is present in the inspected source.

## 2. Internal UI topology is server-rendered Rails plus Turbo/custom elements and Vue islands

- **Statement / locator:** The main Rails layout loads the `application` pack and yields ERB-rendered content (`docuseal/app/views/layouts/application.html.erb:4-19,29-36`); the signing layout loads the separate `form` pack (`docuseal/app/views/layouts/form.html.erb:4-16`). `application.js` starts Turbo, registers many custom elements, and mounts the Vue `TemplateBuilder` and `ImportList` islands (`docuseal/app/javascript/application.js:1-6,63-65,103-160,169-211,261-288`). `form.js` mounts the Vue `Form` as a `submission-form` custom element (`docuseal/app/javascript/form.js:1-21,25-63`). The direct client dependencies declare Turbo, Vue 3, Shakapacker/Webpack, and supporting UI libraries (`docuseal/package.json:4-68`).
- **Status / limitation:** **Observed.** These are internal application UI boundaries; they are not the separately documented `docuseal-form` / `docuseal-builder` integration components.
- **Boundary:** Rails controllers/views ↔ DOM/custom-element bridge ↔ Vue template-builder and signer-form component trees.
- **History target:** `app/javascript/application.js` (`template-builder` registration), `app/javascript/form.js` (`submission-form` registration), `app/views/layouts/application.html.erb`, `app/views/layouts/form.html.erb`.
- **ADR / gap:** **Material documentation gap:** no source document defines the UI layering, supported browser contract, or ownership/versioning of the ERB-to-custom-element-to-Vue boundary.

## 3. Template JSON is a shared, implicit UI/API/domain contract

- **Statement / locator:** The builder receives a template hash selected by `Templates.serialize_for_builder`, including `schema`, `fields`, `submitters`, `variables_schema`, `preferences`, and document metadata (`docuseal/lib/templates.rb:6-8,149-158`, `Templates.serialize_for_builder`). The edit view serializes it into the `data-template` attribute (`docuseal/app/views/templates/edit.html.erb:9-12`); `application.js` parses that attribute and passes the mutable object to Vue (`docuseal/app/javascript/application.js:169-206`). The builder declares only a generic required `Object` for `template` (`docuseal/app/javascript/template_builder/builder.vue:811-815`) and PUTs the nested shape back to `/templates/:id` (`docuseal/app/javascript/template_builder/builder.vue:3523-3562`). `TemplatesController#template_params` independently enumerates the accepted nested keys (`docuseal/app/controllers/templates_controller.rb:89-106`), while `Templates::SerializeForApi` independently exports substantially the same shape (`docuseal/lib/templates/serialize_for_api.rb:5-13,17-30`). Models persist these structures through JSON coders (`docuseal/app/models/template.rb:52-63`).
- **Status / limitation:** **Observed implementation; inferred risk.** The same shape is copied across Ruby serializers, ERB attributes, Vue property access, controller allow-lists, and public API output. A targeted source search found no referenced schema validator or generator binding these copies; contract synchronization and compatibility policy are therefore **unknown**, not proven absent from unavailable material.
- **Boundary:** Template domain object ↔ Rails UI serializer ↔ DOM dataset ↔ Vue builder ↔ Rails update controller; template domain object ↔ public JSON serializer.
- **History target:** `lib/templates.rb` (`TEMPLATE_BUILDER_FIELDS`, `.serialize_for_builder`), `app/controllers/templates_controller.rb#template_params`, `app/javascript/template_builder/builder.vue#save`, `lib/templates/serialize_for_api.rb`.
- **ADR / gap:** **ADR candidate / material gap:** establish one versioned template/field/schema contract and compatibility rule, with generated or validation-backed adapters for UI and external API consumers.

## 4. The public signing UI is a separate route/controller-to-Vue contract

- **Statement / locator:** Public signer routes use `/s/:slug` for `SubmitFormController#show/#update` and related value/download/decline/delegate resources (`docuseal/config/routes.rb:149-170`). The controller deliberately bypasses the normal signed-in application boundary and delegates form authorization and value submission to `Submitters::AuthorizedForForm` and `Submitters::SubmitValues` (`docuseal/app/controllers/submit_form_controller.rb:3-14,17-36,54-94`). The server view derives document/schema/field state and renders the `submission-form` partial (`docuseal/app/views/submit_form/show.html.erb:5-10,132-176`); that partial serializes submitter, schema, fields, values, attachments, invitations, and configuration into data attributes (`docuseal/app/views/submit_form/_submission_form.html.erb:1-5`). `form.js` parses those attributes into Vue props (`docuseal/app/javascript/form.js:21-59`), and the component POSTs form data back to its computed signing path (`docuseal/app/javascript/submission_form/form.vue:141-148,202-220,1608-1646`).
- **Status / limitation:** **Observed.** The flow is a direct server/UI boundary; this evidence does not establish public-link security sufficiency or live behavior. As with the builder, the principal payloads are generic JavaScript objects/arrays rather than a separately versioned contract (`docuseal/app/javascript/submission_form/form.vue:777-850`).
- **Boundary:** Public signer link ↔ `SubmitFormController` ↔ ERB document page/data attributes ↔ Vue signing form ↔ `Submitters` domain services.
- **History target:** `config/routes.rb` signer routes, `SubmitFormController`, `app/views/submit_form/_submission_form.html.erb`, `app/javascript/form.js`, `submission_form/form.vue#saveStep`.
- **ADR / gap:** **Material gap:** document and validate the signer-form payload/version contract, including how web/mobile hosts detect incompatible field/schema changes.

## 5. Submission creation can snapshot the mutable template contract

- **Statement / locator:** Templates persist mutable JSON `fields`, `schema`, `submitters`, and `variables_schema` (`docuseal/app/models/template.rb:52-63`). Submissions have parallel `template_fields`, `template_schema`, `template_submitters`, and `variables_schema` JSON attributes (`docuseal/app/models/submission.rb:56-61`). Creation deep-copies template submitters and conditionally materializes template fields/schema/variables into the submission when recipient customization, completion, variables, or dynamic-document behavior requires it (`docuseal/lib/submissions/create_from_submitters.rb:22-40,53-77,224-246`). Downstream signing reads the submission snapshot when present and falls back to the current template (`docuseal/app/views/submit_form/show.html.erb:5-10`; `docuseal/app/models/submission.rb:127-145,173-175`).
- **Status / limitation:** **Observed.** The source establishes conditional snapshot/fallback semantics, but no explicit compatibility/version field identifies which template-contract version a submission follows.
- **Boundary:** Mutable template definition ↔ per-submission contract ↔ signer UI and serializers.
- **History target:** `Submissions::CreateFromSubmitters.maybe_set_template_fields`, `Submission#schema_documents`, `Submission#fields_uuid_index`.
- **ADR / gap:** **ADR candidate:** define the immutability/versioning rule for in-flight signature requests. The conditional fallback to the current template is a material contract-evolution decision that is not explained in source documentation.

## 6. Community REST implementation and the checked-in OpenAPI document are not one demonstrably aligned contract

- **Statement / locator:** The implemented JSON namespace exposes users, attachments, submitter tracking, submitters, submissions/documents, templates/clone/submissions, tools, and event-query endpoints (`docuseal/config/routes.rb:26-51`). Most integration controllers inherit `Api::ApiBaseController`, which supplies JSON-only behavior, pagination, shared error envelopes, authorization checks, and `X-Auth-Token` lookup (`docuseal/app/controllers/api/api_base_controller.rb:3-19,40-95`). Controllers delegate response shape to explicit serializers such as `Submissions::SerializeForApi` and `Submitters::SerializeForApi` (`docuseal/app/controllers/api/submissions_controller.rb:18-51,54-68`; `docuseal/lib/submissions/serialize_for_api.rb:5-13,18-64`; `docuseal/lib/submitters/serialize_for_api.rb:5-14,24-52`).
- **Statement / locator:** The checked-in OpenAPI 3.1 document is internally versioned `1.0.0`, points only at hosted US/EU servers, and declares `X-Auth-Token` (`docuseal/docs/openapi.json:2-30`). It lists 17 hosted-style paths (`docuseal/docs/openapi.json:47,605,1207,2388,3004,3094,3428,4496,5458,6436,7379,7834,8334,8804,9335,10092,10864`). Several documented creation paths (`/submissions/{pdf,docx,html}` and `/templates/{html,docx,pdf}`) are explicitly classified by Community error handling as Pro-only when unresolved (`docuseal/app/controllers/errors_controller.rb:3-20,27-30`); conversely, implemented Community routes such as tools, events, attachments, and user are not present among the OpenAPI paths.
- **Status / limitation:** **Observed mismatch; applicability unknown.** The OpenAPI file can describe hosted/Pro capabilities and does not state compatibility with release 3.1.7. It cannot be treated as the definitive self-hosted Community contract without vendor evidence. No source generator/link from controllers/routes to this file was found in targeted search.
- **Boundary:** External REST clients ↔ `/api` routes/controllers/serializers; checked-in documentation ↔ hosted and potentially Pro API.
- **History target:** `config/routes.rb` API namespace, `Api::ApiBaseController`, `docs/openapi.json`, `ErrorsController::ENTERPRISE_PATHS`.
- **ADR / gap:** **Material gap / vendor question:** require a release- and edition-specific OpenAPI contract, generation/validation process, base-path statement, deprecation policy, and compatibility evidence. Decide whether organization clients bind to Community endpoints, Pro endpoints, or a separate organization-owned adapter.

## 7. Webhooks have an implemented envelope/event registry, but documentation is a parallel contract

- **Statement / locator:** `WebhookUrl::EVENTS` and `WebhookUrls::EVENT_TYPE_TO_JOB_CLASS` enumerate the same 11 form/submission/template event names (`docuseal/app/models/webhook_url.rb:26-39`; `docuseal/lib/webhook_urls.rb:3-22`). Outbound delivery constructs `{event_type, timestamp, data}` JSON and adds `X-Docuseal-Signature` when absent (`docuseal/lib/send_webhook_request.rb:17-48`, `SendWebhookRequest.call`); signatures are timestamp-prefixed HMAC-SHA256 with a five-minute verifier tolerance (`docuseal/lib/webhook_urls/signatures.rb:3-39`). Webhook data reuses the submitter/submission serializers (`docuseal/lib/submitters/serialize_for_webhook.rb:5-48`; `docuseal/lib/submissions/serialize_for_api.rb:18-64`). The three Markdown references separately enumerate form, submission, and template event schemas (`docuseal/docs/webhooks/form-webhook.md:1-35`; `docuseal/docs/webhooks/submission-webhook.md:1-35`; `docuseal/docs/webhooks/template-webhook.md:1-31`).
- **Status / limitation:** **Observed implementation and documentation; alignment unknown.** No generator or runtime validation binding the Markdown schemas to serializers was found in targeted source search. Consumer implementation and webhook lifecycle guarantees are outside this source packet.
- **Boundary:** Domain events/serializers ↔ outbound JSON envelope/HMAC ↔ organization webhook consumers.
- **History target:** `WebhookUrl::EVENTS`, `WebhookUrls::EVENT_TYPE_TO_JOB_CLASS`, `SendWebhookRequest.call`, `WebhookUrls::Signatures`, `Submitters::SerializeForWebhook`.
- **ADR / gap:** **ADR candidate / material gap:** define the webhook schema/versioning and consumer-compatibility strategy; request a machine-readable, release-bound contract and delivery-semantics evidence before using webhooks in revenue-critical onboarding.

## 8. Embedded web/mobile components are a Pro/external boundary, not the internal Vue implementation

- **Statement / locator:** The README labels embedded signing and embedded form-builder components as Pro and points to separate React/Vue/Angular repositories or public JavaScript documentation (`docuseal/README.md:49-60`). Local embedding references load `https://cdn.docuseal.com/js/form.js` / `https://docuseal.com/js/builder.js` and define `docuseal-form` / `docuseal-builder` attributes and events (`docuseal/docs/embedding/signing-form-javascript.md:1-18,22-50`; `docuseal/docs/embedding/form-builder-javascript.md:1-27,74-79`). The Community `/js/:filename` route is owned by `EmbedScriptsController` (`docuseal/config/routes.rb:222-225`) and returns only dummy `docuseal-builder` / `docuseal-form` elements that display an upgrade message (`docuseal/app/controllers/embed_scripts_controller.rb:3-38`).
- **Status / limitation:** **Observed Community boundary; external implementation unknown.** The separately referenced component repositories/packages were not approved as supporting code and the Pro implementation is out of scope. The internal `template-builder` / `submission-form` Vue islands do not establish the contract or behavior of external `docuseal-builder` / `docuseal-form` packages.
- **Boundary:** Organization web/mobile applications ↔ external Pro component/CDN packages ↔ DocuSeal host; Community route ↔ upgrade placeholder.
- **History target:** `README.md` Pro Features, `EmbedScriptsController::DUMMY_SCRIPT`, `docs/embedding/*`.
- **ADR / gap:** **Deferred vendor validation / decision dependency:** obtain versioned package source/build provenance, supported host/mobile-webview matrix, event/error contract, token/URL trust-boundary design, Community/Pro entitlement terms, and release 3.1.7 compatibility. Decide whether embedding is allowed as a direct vendor dependency or must sit behind an organization-owned integration layer.

## 9. MCP is an additional in-repository protocol adapter over the same domain services

- **Statement / locator:** `/mcp` accepts GET/POST (`docuseal/config/routes.rb:222`). `McpController` parses JSON-RPC methods and dispatches five tools—search/load/create template, send documents, and search documents—whose schemas are collected from controller constants (`docuseal/app/controllers/mcp_controller.rb:3-38`). `Mcp::ProtocolController` advertises protocol version `2025-11-25` and the tools capability (`docuseal/app/controllers/mcp/protocol_controller.rb:11-35`). Each tool co-locates its `inputSchema` with its implementation (for example `docuseal/app/controllers/mcp/search_templates_controller.rb:5-42`; `docuseal/app/controllers/mcp/send_documents_controller.rb:5-67,70-114`) and delegates to the same `Templates`, `Submissions`, serializer, webhook, and search modules used elsewhere.
- **Status / limitation:** **Observed.** The in-code input schemas cover tool arguments, but output payloads are constructed separately in controller methods; no release-independent output schemas or compatibility policy are declared here.
- **Boundary:** MCP clients ↔ JSON-RPC dispatcher/tool schemas ↔ existing template/submission domain modules.
- **History target:** `McpController::TOOL_CONTROLLERS`, each MCP controller `SCHEMA`, `Mcp::ProtocolController#initialize_request`.
- **ADR / gap:** **ADR candidate:** decide whether MCP is inside the target architecture at all. If retained, version and validate both input and output contracts rather than coupling consumers directly to controller-built hashes.

## 10. Unavailable extensions can add routes/configuration through load hooks

- **Statement / locator:** The Community application exposes application-configuration and route extension hooks (`docuseal/config/application.rb:59-61`; `docuseal/config/routes.rb:129-139,222-226`) plus a Devise configuration hook (`docuseal/config/initializers/devise.rb:337`). The Community route file itself does not implement all paths referenced by the hosted OpenAPI or frontend conditional branches.
- **Status / limitation:** **Observed extension seams; intended use inferred; loaded extensions unknown.** These hooks could permit separately supplied code to extend Community topology, but the approved corpus contains no implementation proving which Pro modules use them or their contracts.
- **Boundary:** Inspected Community core ↔ unavailable extension/Pro code.
- **History target:** `config/application.rb` `run_load_hooks(:application_config)`, `config/routes.rb` `run_load_hooks(:multitenant_routes)` and `run_load_hooks(:routes)`.
- **ADR / gap:** **Material architecture gap / vendor question:** request the Pro component/module map, hook contracts, upgrade compatibility guarantees, and the release-specific route/contract delta. Do not infer Pro behavior from Community extension points.
