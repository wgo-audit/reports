# Change-Safety Matrix — Regulated Onboarding Boundary

|---|---|---|---|---|---|

| Signer form bridge | Desktop Cuprite system specs | Partly; test-authored interaction, production-generated output | Mobile/webview/accessibility and generic JSON contract/version drift | All-new-customer onboarding can regress on the target channel | OI-008: supported viewport/browser/webview/accessibility matrix and contract fixtures |
| PDF/audit generation | Completion job creates documents and compares stored SHA-256 metadata; it does not recompute the digest or assert an audit artifact | No; certificate and artifacts are production-generated | Signed/unsigned, PKI/TSA/LTV, tamper, multi-signer, audit content, failure/retry conformance | Signed agreement or evidence may be unusable despite a green suite | OI-006: specialist-approved known-answer artifacts and independent verifier |
| PDF signature verification | Settings UI render test | No | Validity/error/trust-chain behavior is untested | Operators or users may misinterpret evidence validity | OI-006: known-valid/invalid/altered/expired/revoked/malformed cases |
| Completion jobs and stores | One completion job spec; source lock/retry logic | No target-topology oracle | Concurrency, crash, stale locks, duplicate/lost work, SQL/blob/queue reconciliation | Revenue onboarding can be partial or inconsistent | OI-003/OI-006 failure and recovery tests |

## Safe-Change Acceptance Boundary

For further evaluation, existing green CI is a useful baseline. Before production approval, the organization needs an acceptance layer it owns: release/edition-specific contracts; independent artifact verification; failure/recovery and migration tests against the target topology; mobile/browser/accessibility coverage; measurable test/coverage outputs; and immutable artifact promotion. These requirements assess the target integration and do not characterize unavailable Pro code as defective.
