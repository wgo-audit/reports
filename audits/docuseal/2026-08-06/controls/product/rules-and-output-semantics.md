# Rules And Output Semantics

## Evidence Boundary

Pinned Community source only establishes implementation. No live values, configured edition, output artifact, or specialist acceptance was obtained. Evidence: [PV-E-001–PV-E-004](../../evidence/packets/product-value-source-inspection.md).

| Rule / control | Runtime consumer and durable effect | Output meaning | Material unknown / closure |
|---|---|---|---|
| `completed=true` with required-field validation | `Submitters::SubmitValues` sets signer completion, captures IP/UA/timezone, creates `complete_form`, and enqueues completion after transaction. | Signer row is complete; it is not proof that all signers, artifacts, emails, or webhooks are complete. | Define the organization-facing completion state and test job failure/retry edges. |
| Submission completion | `Submissions.maybe_update_completed_at` marks the submission complete after all non-viewer submitters complete. | SQL workflow completion precedes async audit/email/webhook finalization. | Do not trigger revenue finalization solely from the SQL timestamp without readiness/reconciliation proof. |
| Signer order | Preserved order blocks later signers and sends the next invitation after prior completion; random can invite in parallel. | Availability and partial-document exposure depend on workflow configuration. | Product/legal authority must choose ordered/parallel and partial-document visibility policy. |
| Signature modality and disclosure | Signature fields can accept drawn, typed, uploaded/camera, or reusable signature images. The disclosure link is conditional, defaults off, and is not enabled by the Community submission partial. | A stored signature image and `complete_form` event show implemented interactions, not durable consent/disclosure acceptance, signer identity, intent, or legal effect. | Product/legal authority defines modality, disclosure, consent/intent, evidence, accessibility, and correction rules; implement and test the accepted contract. |
| Email 2FA | Template/submitter preference requires OTP or signed token; success creates `email_verified` and a 12-hour encrypted cookie. | Proves possession of an email channel under the implemented protocol, not a verified legal/KYC identity. | Threat-model, test, and obtain specialist sufficiency determination. |
| Phone 2FA / SMS | Parameters and event names are accepted, but the inspected Community route is not an implementation and the SMS settings UI is Pro-only. | No Community phone-assurance result can be claimed. | Vendor supplies Pro implementation and assurance evidence; organization validates. |
| File/image attachment intake | Signer file/image fields upload blobs and reject a source-defined list of dangerous filename extensions. | Generic attachment acceptance does not mean a KYC document is authentic, malware-free, bound to the signer, or retained under an approved policy. | Define accepted formats/content validation, malware scanning, identity binding, rejection/fallback, privacy, and retention; test the resulting pipeline. |
| Signing reason and PKCS | Result PDF signing occurs only when both a discovered signing reason and PKCS material exist. Audit PDF signing requires PKCS but not the per-signature reason. | Outputs may be hashed but unsigned, or cryptographically signed under deployment trust material. | Make unsigned/signed modes explicit; fail closed if the approved workflow requires cryptographic signing. |
| Timestamp server | When configured, signing parameters use a timestamp handler; otherwise no TSA is attached. | Local signing time and a trusted RFC 3161 timestamp are not equivalent. | Select TSA, custody, outage behavior, and verification acceptance. |
| Result SHA-256 | Generated result attachment stores a SHA-256 and completion worker copies it to `completed_documents`. | Hash binds bytes, but the verification response only reports membership, not tenant/submission identity. | Add or externally retain tenant/submission/artifact provenance and test purge/restore behavior. |
| Audit PDF | Generated after final signer from current submission/event state; signed only when PKCS exists. | Human-readable evidence snapshot. No append-only/immutability control was found in the inspected source, so an immutable chain is not established. | Define authoritative record, immutability, regeneration, retention, and legal hold. |
| Webhook success | Remote response under 400 marks the local event successful; failures retry with backoff. | At-least-once remote side effect is possible; UUID is local event identity, not remote exactly-once proof. | Version schemas; require consumer dedupe, reconciliation, replay ownership, and exhaustion alerts. |
| API `checksum_status=verified` | Global `CompletedDocument.exists?(sha256:)`; signature messages use current account trust certs. | “verified” means only generated-hash membership; it does not identify the submission/tenant or mean every signature is trusted. | Rename/separate results or add provenance-rich response and acceptance tests. |
| Archive vs permanent delete | Archive retains records and emits event; hard delete removes main workflow records with unresolved completion/delivery ledger cleanup. | Record availability and evidentiary retention are policy-sensitive and not defined by UI wording alone. | Create lifecycle/retention/legal-hold matrix and verified deletion tests. |

## Rule Conflicts

- Checked-in API descriptions accept phone 2FA/SMS and hosted endpoints while Community source does not implement the phone path and public pricing calls API/SMS Pro. Applicability is unresolved, not a failed Community behavior.
- Public “legally binding,” “independently verified,” and “unaltered state” wording is broader than the source-bounded output meanings above. These remain vendor promises requiring edition-specific artifacts and specialist review.
- Issue #384 and #575 are reporter observations that could affect partial-document and timestamp acceptance. They are test cases, not confirmed 3.1.7 findings.
