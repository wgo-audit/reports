# Security and Privacy

## Audit Question, Depth, And Evidence Boundary

This detailed review asks whether Plausible can support privacy-first service measurement without reintroducing tracking practices the library intends to avoid, and whether Run or Subscribe can collect, retain, protect, and govern visitor data responsibly. The cutoff is 2026-08-20 at onboarding start, America/Toronto. Evidence is the approved `primary-code` snapshot at commit `9cc669b97ece3ecd37fcb3950791cb3873d7944d`, cutoff-effective public privacy/instrumentation guidance, and current hosted-security pages used only as post-cutoff validation. The assumed 18 properties, 2 million visits, 14 million page views, and 25 staff were not verified and were not treated as security-control evidence.

The review covered source-visible visitor processing, pseudonymous identity, storage fields, staff and alternate access paths, deletion, diagnostics, ingestion abuse controls, dependency/release tooling, and trust-anchor production/consumption. It did not inspect live visitor traffic, library configuration, ingress, IAM, secrets, backups, hosted internal systems, contracts, replacement products, or legal applicability; it did not install dependencies, scan services, run a penetration/load test, or make a certification claim.

## Coverage And Material Gaps

The source establishes a privacy-minimizing default path and several useful authorization, credential, filtering, and deletion mechanisms. It does not establish the library's effective data dictionary, URL/property content, retention, roles, 2FA, keys, shared/public links, report recipients, offboarding, proxy/header trust, deletion completion, backups, or deployed artifact. Close the governance decision through [OI-008](../../controls/open-items.md#oi-008), claim semantics through [OI-009](../../controls/open-items.md#oi-009), the diagnostic path through [OI-010](../../controls/open-items.md#oi-010), and edge integrity through [OI-011](../../controls/open-items.md#oi-011). Deployment and artifact identity remain [OI-001](../../controls/open-items.md#oi-001) and [OI-005](../../controls/open-items.md#oi-005).

Hosted security statements are public assertions, not independent operating evidence. No approved live edge evidence exists, so no edge-exposure view was created. Deep request-path exploitability belongs to Application Security; live ingress, IAM, registry, backup, and runtime effectiveness belong to Cloud Security; legal applicability requires qualified privacy/legal review.

## Mandate-Relevant Strengths

- Raw IP address and full User-Agent are transient ingestion inputs; the reviewed ClickHouse schemas store a daily-derived visitor identifier and coarse location/client attributes rather than those raw values ([E-024](../../evidence/evidence-ledger.md#e-024)). This is a meaningful privacy advantage, not proof of legal anonymity.
- Request, URL, and custom-property counts/sizes are bounded, and public guidance tells customers not to send personal information in custom properties and documents URL redaction ([E-023](../../evidence/evidence-ledger.md#e-023), [E-024](../../evidence/evidence-ledger.md#e-024)).
- Browser/API boundaries include session, CSRF, membership, site, scope, and feature checks; API keys are randomly generated, hash-stored, scoped and rate-limited, and sessions can be revoked ([E-025](../../evidence/evidence-ledger.md#e-025)).
- Site removal records pending deletion and a scheduled worker performs site-scoped ClickHouse deletion, giving Run an inspectable lifecycle mechanism even though completion/backups remain unverified ([E-025](../../evidence/evidence-ledger.md#e-025)).
- Lockfiles, commit-pinned Actions, Dependabot schedules, content-digest image assembly, and a public vulnerability-reporting route provide useful maintenance and provenance building blocks ([E-028](../../evidence/evidence-ledger.md#e-028), [E-029](../../evidence/evidence-ledger.md#e-029)).

### Decision Insights

1. **Run remains plausible only with owned governance and live verification.** The default implementation supports privacy-first analytics, but configuration controls the fields, alternate access, retention, and edge integrity. Approve [OI-008](../../controls/open-items.md#oi-008) and verify [OI-011](../../controls/open-items.md#oi-011) before expanding search/registration instrumentation.
2. **Subscribe transfers operation, not accountability.** Hosted public claims cannot close the library's security/privacy decision. Procurement should obtain dated service-specific evidence for access, encryption, deletion, backups, incident handling, subprocessing, vulnerability management, and contractual responsibilities; use [OI-008](../../controls/open-items.md#oi-008) as the common acceptance contract.
3. **Replace is not evidenced as safer.** No alternative was assessed. Use the same data-minimization, access, deletion, anti-poisoning, assurance, and export requirements as bounded selection criteria rather than treating absence of evidence for another product as a strength.
4. **Correct the diagnostic secret path independently of option selection.** For Run, disable or isolate/redact the optional Google/Sentry combination until [OI-010](../../controls/open-items.md#oi-010) is closed; for Subscribe, obtain evidence of equivalent diagnostic scrubbing.
5. **Do not rely on the absolute one-day privacy wording until reconciled.** [OI-009](../../controls/open-items.md#oi-009) is a vendor/privacy clarification, not evidence that the bounded cross-midnight implementation is unacceptable.

## Material Omissions, Unknowns, And Auditor Questions

The material decision dependency is [OI-008](../../controls/open-items.md#oi-008): the Director of Digital Services, privacy/records authority, and security authority must approve the smallest acceptable analytics data/access/retention contract before option acceptance or added instrumentation. This route requires a governance decision and a synthetic non-production validation, not staff interviews or live-traffic inspection. Applicable legal obligations remain a separate specialist question; this review makes no legal conclusion.

The public daily-salt wording requires vendor/privacy clarification through [OI-009](../../controls/open-items.md#oi-009). Diagnostic exploitability and complete request/sink coverage are routed to Application Security; ingress/header trust, hosted controls, registry/IAM, backups, and runtime deletion are routed to Cloud Security and procurement. No replacement product was approved, so Replace has no comparative security evidence. [OI-002](../../controls/open-items.md#oi-002) and [OI-007](../../controls/open-items.md#oi-007) remain unanswered and were not inferred from security evidence.

## Reconciliation

Architecture's source/live/hosted separation is preserved: the reviewed implementation is not the deployed library environment and does not establish hosted operation. Product Value's role, shared-link, API, export, and report-recipient surfaces are reconciled here as intentional governance boundaries, not authorization defects. Code Quality's exact-commit and release evidence supports source provenance only; the library's consuming verifier remains open.

A material apparent mismatch exists between cutoff-effective public daily-salt wording and source lifecycle/session semantics ([OI-009](../../controls/open-items.md#oi-009)). Current hosted security and disclosure pages are explicitly post-cutoff public validation and were not used to rewrite cutoff state. No prior Security and Privacy report existed. The quality review's one requested revision was applied; no unresolved quality-worker issue remains.

## Bounded Conclusion And Downstream Guidance

Plausible's reviewed source provides a credible privacy-first foundation for aggregate service measurement: raw IP/User-Agent are not analytics-storage fields, identifiers are daily-derived, roles/scopes and revocation exist, and collection/deletion/abuse-control mechanisms are inspectable. The evidence does not establish responsible library operation, hosted control effectiveness, legal compliance, or comparative replacement safety. Run should remain conditional on OI-008/OI-011 and deployed provenance; Subscribe should pass the same governance contract plus security/privacy/procurement evidence; Replace should be judged against those same requirements.

Application Security should use the diagnostic and ingestion paths for deeper source analysis without assuming live exposure. Cloud Security should use the identity/data-flow and supply-chain views for option-specific edge, IAM, registry, backup, deletion, and runtime verification without treating public claims as control proof. Business Continuity should carry retention/deletion and access-transfer dependencies without inferring recovery from source mechanisms.
