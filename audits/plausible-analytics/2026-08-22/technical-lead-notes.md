# Technical Lead Notes

## Current Technical Position

The pinned source is an understandable but operationally broad monorepo. One Phoenix/OTP application produces CE and Cloud/EE profiles through compile-time paths. PostgreSQL owns relational, control, and Oban state; specialized ClickHouse repositories own analytics reads, ingestion, asynchronous insert, and deletion. Event/session persistence supports embedded, remote, and relay modes with deterministic rollout, session sharding, caches, and in-process buffers. Oban provides scheduled and asynchronous jobs. One tracker source compiles multiple web, legacy, npm, and support variants. See the [system component/data flow](controls/architecture/diagrams/system-component-and-data-flow.md) and [ADR register](controls/architecture/adr-register.md).

The repository has substantial declared change-safety breadth: EE/CE database-backed ExUnit partitions, application browser E2E, Jest, generated type checks, static/type/style checks, migration change segregation, and three-engine tracker Playwright. Pinned merge-group GitHub jobs were green. The public API did not expose test-case counts, coverage, retries, or logs; application tests could not run locally because toolchains, dependencies, and services were absent and restore/install was not authorized. Local application tests were **0 passed, 0 failed, 0 errors, 0 skipped**. See the [change-safety matrix](controls/quality/change-safety-matrix.md).

**Overall technical judgment:** this is a high-quality, deliberately engineered system maintained by a team showing meaningful rigor. The architecture is appropriately specialized for an analytics product without becoming illegible; the test/review surface is substantial; and the code contains multiple signs of experienced operational design. The findings below are useful improvement targets, not evidence that the team or architecture is generally weak.

The audit's safe-change boundary is source-local. Persistence, deletion, migrations, release/promotion, live Cloud configuration, recovery, capacity, and approval-sensitive changes should be learned from the team after joining. The public absence of those private details is neutral; it does not imply missing controls and should not be used as an offer-stage negative.

Affirmative controls should be preserved: scoped tenant queries, random/digested tokens, session expiry/revocation, role and shared-link constraints, direct-HTTP SSRF IP pinning/per-redirect validation, full-SHA action pins, digest-pinned Docker bases, lockfiles, non-root container execution, broad profile/database/browser tests, query sampling/time bounds, Oban retry/rescue, health/telemetry definitions, and public advisory/release correction channels. Taken together with substantive PR review and coherent product behavior, these are the strongest available indicators that the team is careful rather than sloppy.

Source-visible capacity controls are not a capacity result. The k6 file declares 6,000 synthetic event requests/second for one minute, and PR #5380 reports roughly 12,000 requests/second on one developer machine. Neither has a retained environment/result packet or Cloud applicability. Session serialization, per-process buffers, local ETS limits, ClickHouse pools, single-concurrency queues, exports without ordinary query limits, and tenant/custom-retention obligations make effective capacity topology- and workload-dependent. See [Capacity and Degradation](controls/scalability/capacity-and-degradation-view.md).

## Safe Evolution Priorities

1. **Contain known destructive/disclosure paths.** Merge and release the worker-scoped import fix with destructive regression coverage; redact Sentry context; reconcile versions/data and retained vendor events.
2. **Protect privileged build and fetch boundaries.** Separate write credentials from PR execution, disable persisted credentials, prove PAT history/scope, and enforce SSRF policy at Browserless egress with isolation and negative tests.
3. **Learn the operational control plane before changing it.** Trace required checks to artifact, promotion, migration, deployed digest, telemetry, rollback, and approval with the current owners. Establish only the missing baselines that prove useful internally.
4. **Validate important data outcomes proportionately.** Exercise event durability/loss, ClickHouse mutation completion/reconciliation, backup/restore, and export lifecycle as part of normal reliability ownership—not as a presumption that they fail.
5. **Extend the existing quality discipline.** Obtain case-level results, coverage, retry/flake history, fixture lineage, escaped defects, and branch rules. Add the smallest high-value journey or negative cases that the current evidence shows are missing.
6. **Build normal capacity and cost baselines.** Measure per-tenant/fleet demand, queues, ClickHouse profiles/storage, provider limits, cost, and SLOs, then invest only where actual headroom or customer needs justify it.
7. **Make useful decisions transferable.** Validate reconstructed ADRs with the team, define supported CE/EE/tracker combinations, and improve successor coverage where internal evidence—not public absence—shows a real need.

The [complexity and time-to-safety map](controls/maintenance/complexity-skills-and-time-to-safety.md) gives six evidence gates without inventing a staffing or elapsed-time estimate. The public contribution sample is useful only for prioritizing consent-aware ownership and successor verification.
